## What's new in 0.10.0

### Katana's OpenID Connect and JWT middleware (Entra ID)

- **webForCore builds the rest of Katana 4.2.3's security middleware**: `webForCore.Microsoft.Owin.Security.OpenIdConnect`,
  `.Jwt`, `.WsFederation`, `.ActiveDirectory`, `.Google`, `.Facebook`, `.MicrosoftAccount` and `.Twitter`, from
  Microsoft's source, unchanged, with Microsoft's identities. A customer application signs in with Entra ID (Azure AD)
  through `UseOpenIdConnectAuthentication` and protects its Web API with JWT bearer tokens. Before, applications kept
  Microsoft's packages, which depend on IdentityModel 5 while every webForCore application has IdentityModel 8.19.1
  through CoreWCF: with the IdentityModel 5 packages a packages.config conversion lists, restore failed with `NU1605`
  (the smoke test's Bonobo Git Server, with WS-Federation), and without them Katana built for 5.x ran on a mix of
  IdentityModel 5 and 8 assemblies. webForCore's are built against 8.19.1, so an application has one IdentityModel; the
  source needed no change. Replace the packages with webForCore's, remove the application's IdentityModel 5 references,
  and `Startup.Auth.cs` stays as it is ([MIGRATING.md](../MIGRATING.md#packages-that-need-more-than-a-reference)).
- **An OpenID Connect gate** runs the "Work or School Accounts" template's startup as a customer application configures
  it (code id_token with form_post, the code redeemed, `SaveTokens`, notifications that change the outcome, its own
  ticket and state formats, JWT and IdentityServer3.Contrib.AccessTokenValidation bearer tokens) against a test OpenID
  Connect provider, on Linux and Windows: sign-in and the claims in `User`, sign-out to end_session, and the rejection
  of tampered, expired, wrongly issued or addressed tokens and wrong or missing nonces. CI's `iis-compare` job runs the
  same scenarios against the same application on IIS 10 with Microsoft's packages and compares the responses.
- **Entra ID behind a proxy that ends TLS:** set `ASPNETCORE_FORWARDEDHEADERS_ENABLED=true` for `webforcore-host`, so
  that Katana's `SameSite=None` nonce cookie is `Secure`; browsers drop it otherwise, and every sign-in fails with
  `OpenIdConnectProtocolInvalidNonceException`, as on IIS behind such a proxy.

### `<machineKey>` output shared with .NET Framework 4.8

- **What webForCore protects with a `<machineKey>` reads on .NET Framework 4.8 with the same keys, and the reverse**
  (#191), so an application can move one service at a time, or roll back, without signing users out:
  `FormsAuthentication` tickets, `MachineKey.Protect`/`Unprotect` (with and without purposes), `MachineKey.Encode`/
  `Decode`, and Katana's cookies on `Microsoft.Owin.Host.SystemWeb`, a plain `UseCookieAuthentication` one and ASP.NET
  Identity's application cookie with `SecurityStampValidator`, which the host protects with the machine key, not DPAPI.
  Checked for validation SHA1, HMACSHA256 and HMACSHA512, decryption AES and 3DES, and `compatibilityMode`
  Framework20SP1, Framework20SP2, Framework45 and `<httpRuntime targetFramework="4.5">`'s default. A new gate,
  `MachineKeyInteropTests`, runs a sample with each `<machineKey>` and reads what .NET Framework 4.8 protected (committed
  data), and CI's `machinekey-framework-interop` job has .NET Framework 4.8 read what webForCore protected in the same
  run. Output with a random IV is compared by reading it; output that is the same on every call is compared byte for
  byte. Not shared, and documented ([IIS-COMPATIBILITY.md](../IIS-COMPATIBILITY.md#authentication),
  [MIGRATING.md](../MIGRATING.md#5-configuration)): an application without `targetFramework` and `compatibilityMode`
  (Framework20SP1 on .NET Framework, Framework45 on webForCore), and `IsolateApps` or `IsolateByAppId` after an explicit
  key.
- **`validation="HMACSHA256"` (the default), `"HMACSHA384"` and `"HMACSHA512"` compute that HMAC in the Framework20
  modes and in `MachineKey.Encode`** (#191). webForCore's managed version of .NET Framework's native HMAC-SHA1 returned
  HMAC-SHA1 padded with zeros for them, where .NET Framework falls back to the HMAC the configuration names: forms
  tickets with `compatibilityMode="Framework20SP1"` or `"Framework20SP2"`, view state MACs in those modes, and every
  `MachineKey.Encode` output were rejected by .NET Framework, and .NET Framework's by webForCore ("Unable to
  validate data"). Such output written by an earlier webForCore doesn't validate any more: users of an application in
  those modes sign in once again.

### Fixes

- **A request whose path has a `(` keeps its headers** (#170). A path with a `(` that isn't a cookieless-session path
  (`/(S(...))/...`) reached the application without any header IIS has no index for: `Prefer`, `X-Requested-With`,
  `OData-*`, `X-HTTP-Method-Override` and any `X-...` were missing from `Request.Headers`, `ALL_RAW` and Web API's
  `HttpRequestMessage.Headers`. OData keys are in parentheses (`/People(FirstName='Kate',LastName='Jones')`), so a
  `PATCH` with `Prefer: return=representation` answered 204 instead of 200 with the entity (the smoke test's
  `odata-samples-compositekey`). IIS keeps them whatever the path, and CI's `iis-compare` job now checks this against
  IIS 10.
- **A reference to an assembly without a strong name binds whatever the version** (#171), as on .NET Framework, where
  fusion checks versions only for strong-named assemblies. A library built against `Nancy, Version=0.21.1.0,
  PublicKeyToken=null` failed with `FileNotFoundException` when the application deploys Nancy 0.20.0 (JabbR). A
  strong-named reference to a lower deployed version still needs its binding redirect, which isn't applied yet (#158).
- **A request running when the application restarts runs to its end** (#181), in the old worker, while the new one
  serves new requests, as on .NET Framework, where `HttpRuntime` waits for an old domain's requests for
  `<httpRuntime shutdownTimeout>` (90 s by default) and, in the classic pipeline, for those still running after that
  too; IIS 10 runs them to their end in both pipelines. It was cut 5 to 30 s after the restart:
  `<hostingEnvironment shutdownTimeout>` (30 s), which on .NET Framework is the wait for the application's registered
  objects, not for its requests, aborted it, and the worker's own shutdown cut it 30 s after the restart at the most.
  DNN's installer, which streams its progress and installs packages into `bin`, didn't finish. WebSockets are aborted
  as soon as the application's registered objects have stopped, as on IIS, instead of after
  `<hostingEnvironment shutdownTimeout>`. webforcore-host gives an old worker its drain time beyond its shutdown time
  limit. CI's `iis-compare` job checks this against IIS 10.
- **`Response.Write` with `BufferOutput = false` works** (#184). It threw "The buffer is not associated with this pool"
  in `HttpResponseBufferElement.Recycle`, and the response never ended: Bonobo Git Server's smart HTTP (every clone,
  fetch and push) hung. webForCore's response buffers come from `ArrayPool<byte>.Shared` (.NET Framework's were
  unmanaged), and every buffer went back to the pool, also the arrays the writer only wraps. Now only rented buffers go
  back, as the unmanaged ones were freed, and not while the output cache keeps them; a cached response could be
  sent with another response's bytes. An application's own output cache provider got the whole pool buffer and served
  the page followed by whatever was left in it; it gets the page's bytes, as on .NET Framework.
- **A response that fails while it is being sent ends or is aborted** (#184). When the last chunk of a response
  ASP.NET chunked itself (unbuffered output) couldn't be sent, and the error couldn't be written into it either, the
  client waited for ever; the worker aborts the connection now, so the client sees the response fail.

### Migration guide

More of what the smoke test's migrations found, in [MIGRATING.md](../MIGRATING.md), [NAMESPACES.md](../NAMESPACES.md)
and [AGENT-MIGRATION.md](../AGENT-MIGRATION.md) (its search list and symptom table):

- **Code:** libraries resolve relative paths against `bin_dotnet/`, so a log written there restarts the application at
  every line (mojoPortal's log4net, #173); `AppDomain.RelativeSearchPath` is null (use `HttpRuntime.BinDirectory`,
  #177); `SecurityProtocolType.Ssl3` throws on .NET (#176); LINQ to SQL's generated SQL, `GetCommand().CommandText` as
  well as `DataContext.Log`, has `\n` on Linux (#175).
- **Views:** a Razor 1 view with `@` before a C# keyword in a code block doesn't parse on Razor 3: wrap it in `@( ... )`
  (#174).
- **Libraries:** any prebuilt .NET Framework library that uses `CallContext` fails with `TypeLoadException`, not only
  Log4Net.Async: SimpleInjector 3.1's ExecutionContextScoping (use 3.3.2, #178).
- **Session state stays in process unless it was out of process on IIS** (#180). The guide's `Program.cs`
  ([MIGRATING.md](../MIGRATING.md#4-programcs), AGENT-MIGRATION.md Phase 2 step 6, the README) added
  `AddDistributedMemoryCache()` and `UseAspNetCoreSessionProvider()` to every application that used `Session`. That
  made session state out of process, as StateServer and SQLServer were on IIS, so every value had to be serializable:
  MVCForum, which keeps a view model that isn't `[Serializable]` in MVC's `TempData`, failed the request after creating
  a topic or deleting a member ("Unable to serialize the session state"). Without the provider, session state is in
  process, in .NET Framework's own `InProcSessionStateStore`, as `<sessionState mode="InProc">` (the default) was on
  IIS: values are the objects themselves. The guide now adds the provider only where `<sessionState mode>` was
  `StateServer`, `SQLServer` or `Custom`, or to scale out, says that its values must be serializable, and has the
  error in its symptom tables. The MVC sample and the TestApp run in process; the Web Pages sample uses the provider in
  place of `StateServer`, and the gate checks both.
