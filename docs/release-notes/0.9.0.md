## What's new in 0.9.0

### LINQ to SQL

`System.Data.Linq` 4.0.0.0 is provided, as Microsoft's .NET Framework 4.8 source (microsoft/referencesource) built for
.NET 10 on webForCore's System.Data.SqlClient (#142). It is the `webForCore.Data.Linq` package, which the `webForCore`
package brings, as .NET Framework has it in the GAC. `DataContext`, `Table<T>`, attribute and XML mapping,
`EntitySet`/`EntityRef`, change tracking and optimistic concurrency, `CompiledQuery`, stored procedures and functions,
`DataLoadOptions` and `Binary` work against SQL Server, on Linux and Windows.

- **Errors are .NET Framework's.** Referencesource doesn't include the classes .NET Framework generated for LINQ to SQL's
  errors. webForCore generates its own from data read from .NET Framework 4.8's `System.Data.Linq.dll` (names, messages
  and exception types), so each error has .NET Framework's exception type and message: a query with a method SQL can't
  express throws `NotSupportedException` ("Method '...' has no supported translation to SQL."), as on .NET Framework.
- **Applications that failed before:**
  - Web API OData's `ODataConventionModelBuilder.GetEdmModel()` needs `System.Data.Linq` for its `Binary` mapping, so
    OData applications failed in `Application_Start` (the smoke test's `odata-samples-compositekey`).
  - A web.config that lists `System.Data.Linq` in `<compilation><assemblies>` (mojoPortal, Subtext) was a
    Configuration Error on every page. Both 3.5.0.0 and 4.0.0.0 now resolve.
- **Limits:** SQL Server only. SQL Server Compact (`.sdf`) isn't available, and a `.mdf` file path or LocalDB in
  `new DataContext(...)` works only on Windows with LocalDB installed. `LinqDataSource`, MVC's `LinqBinaryModelBinder`
  and Dynamic Data's LINQ to SQL model provider are still compiled out. `DataContext.Log` writes SQL with the platform's
  newline. See [NAMESPACES.md](../NAMESPACES.md#other-assemblies).

### File change monitoring on Linux

- **Sites with many folders run.** Each folder System.Web monitored (for a cache dependency, a web.config, a view a
  view engine looks for) took an inotify instance of its own, and many took two, out of the user's 128
  (`fs.inotify.max_user_instances`). Orchard 1.10 with its 69 modules used all 128 during its first request, and Kooboo
  CMS and nopCommerce workers held 48 or more; their requests then failed with "Failed to start monitoring changes ...
  The configured user limit (128) on the number of inotify instances has been reached". The folders inside the
  application's folder now share three recursive watchers of it, which tell each folder of the changes its own
  watcher would have seen, so a worker holds a handful of instances whatever the site's size (7 with 200 monitored
  folders), and the same changes restart the application (#145, #152).
- **`<httpRuntime fcnMode>` applies** (#146). It was ignored: `Single` watches the application's folder with one
  recursive watcher, and `Disabled` turns file change monitoring off, so changes (Web.config's included) don't
  restart the application, as on IIS.
- **`fcnMode="Single"` on Windows** (#167). A freshly copied site restarted at its first request: Windows reports
  each folder files were copied into as modified the first time the application opens it (it writes the folder's
  deferred LastWriteTime then), and the application opens all of `bin_dotnet`'s while it starts. It no longer does, on
  Windows as on Linux, and both restart on the same changes as IIS 10 does in each mode (`bin_dotnet` as `bin`). IIS 10
  is told of the same folders at a copied site's first request, and restarts for them in some runs and not in others.
  Using `Default` on Windows is no longer needed.
- **Docs:** [IIS-COMPATIBILITY.md](../IIS-COMPATIBILITY.md#process-model) said a worker takes about 15 instances
  (#107), which held for small sites only. It now gives the count and what to raise if a machine runs many
  applications as one user.

### Request handling as IIS does it

Checked against IIS 10 in CI: `test/webForCore.Requests.Sample` is served by IIS as it is and by webForCore, and the
responses are compared ([TESTING.md](../TESTING.md#compared-with-iis-10)).

- **Escaped characters in a path reach the application** (#126). A path with a space or a non-ASCII character
  (`/Product/Convertible%20Car`, Wingtip Toys' product links) was an empty 400. `Request.Path`, `FilePath`, `PathInfo`
  and `RawUrl` are now decoded, as IIS gives them; `requestPathInvalidCharacters` (`%`, `&`, `:`, ...) get ASP.NET's
  400 page and double escapes request filtering's 404.11, as on IIS. `PathInfo` starts after the page
  (`/Page.aspx/extra/path` was 404).
- **`Request.RawUrl` is the URL asked for** (#127): `/` for a directory whose default document serves it, while `Path`
  is the document's (`/default.aspx`, the name IIS's list gives it). FriendlyUrls no longer redirects `/` to
  `/Default` (the Visual Studio Web Forms template). A directory's redirect to its trailing slash is to an absolute
  URL, as IIS's.
- **A file asked for in another case is found, every time** (#140), as on IIS: on Linux it was a 404 until the file had
  been asked for in its own case (nopCommerce's product thumbnails).
- **`Response.End()` leaves the response to `EndRequest`** (#129): forms authentication turns a 401 ended with
  `Response.End()` into its redirect to the log-in page (`WebSecurity.RequireAuthenticatedUser`, the WebMatrix
  Starter Site), and every module's `EndRequest` can still change the response after `End()`, `Redirect(url, true)`
  and `Server.Transfer`.

### Assembly identities are Microsoft's

Every assembly in webForCore's packages now has the identity of the Microsoft assembly it replaces: name, version,
culture and public key token (#141). Libraries built against Microsoft's assemblies compile and bind against
webForCore's only then: SmartStoreNET's bundles go through BundleTransformer, built against System.Web.Optimization
1.1.0.0 (`31bf3856ad364e35`), and failed to build (`CS0012`, `CS0039`) against webForCore's 11.0.0.0 with the token
`b03f5f7f11d50a3a`. CI now compares every packaged assembly with Microsoft's, read from Microsoft's NuGet packages
(`tools/ci/check_assembly_identities.cs`).

- **System.Web.Optimization** and **Microsoft.AspNet.Web.Optimization.WebForms** are 1.1.0.0 and **WebGrease**
  1.6.5135.21930, with the token `31bf3856ad364e35` (they were 11.0.0.0, `b03f5f7f11d50a3a`).
- **System.Web.Extensions, System.Web.Services, System.Web.Mobile, System.Web.RegularExpressions,
  System.Web.ApplicationServices and System.Web.DynamicData** are 4.0.0.0, as on .NET Framework (they were 11.0.0.0).
  System.Web.ApplicationServices, System.Web.DynamicData and System.Web.DataVisualization have .NET Framework's token,
  `31bf3856ad364e35` (they had `b03f5f7f11d50a3a` and webForCore's own `6b8e2037dda5564b`), so BinaryFormatter
  streams (session state, view state) name them as .NET Framework does.
- **MVC, Web API and CORS** are 5.3.0.0, **System.Net.Http.Formatting** 6.0.0.0 and **MVC Futures** 5.0.0.0, the
  versions Microsoft released (they were the source's development versions, 5.3.1.0 and 6.0.1.0).
- System.Web stays 11.0.0.0, above the shared framework's 4.0.0.0 facade of the same name, and
  System.Configuration.ConfigurationManager 14.5.0.0, above the package of that name; references to Microsoft's
  versions bind to both.

### SignalR's hub proxy names its version

`/signalr/hubs` begins `ASP.NET SignalR JavaScript Library 2.4.3`, as Microsoft's 2.4.3 serves it, instead of the
template's `[!VERSION!]` (#118, SignalR's samples). webForCore's build now writes the version into the template, as
SignalR's own build did on Windows, and the embedded script is byte for byte Microsoft's.

### CoreWCF's source generator stays out of applications

An application with a WCF `[ServiceContract]` and a `LangVersion` below 11 (`7.3`, as MIGRATING.md says for a project
that set none) failed to build: CoreWCF's source generator, which reached every application through the `webForCore`
package, wrote C# 11 code for each contract (`CS8370: Feature 'file types' is not available in C# 7.3`; C1 CMS's log
service, #134). webForCore's CoreWCF dependency no longer brings CoreWCF's build assets. An application that references
CoreWCF itself still gets them.

### Assembly loading

- **`BuildManager.GetType(typeName, throwOnError: false)` returns null for an assembly that isn't deployed**, as on
  .NET Framework, instead of throwing `FileNotFoundException` (#137). So do System.Web's other lookups that don't
  throw (profile `inherits`, view state of typed collections, static objects, `HostSecurityPolicyResolverType`). An
  assembly that is there but can't be loaded still throws, and `throwOnError: true` throws .NET Framework's
  `FileNotFoundException` or `TypeLoadException`. DNN Platform 9 failed at start twice: ClientDependency's module (its
  MVC filter is in an assembly DNN doesn't deploy) and DNN's registration of providers from packages that aren't
  installed.
- **web.config's `<runtime><assemblyBinding><probing privatePath>` is applied** (#147): its folders, below the
  application's, are searched after the build output, in fusion's order, so `Assembly.Load` finds assemblies there.
  Orchard 1.x loads every module from `App_Data/Dependencies` that way. An `AppDomain.AssemblyResolve` handler that
  loads from those folders, written to work around it, can be removed. What else of `<assemblyBinding>` applies is in
  [NAMESPACES.md](../NAMESPACES.md); a binding redirect down to a lower version and `<codeBase>` don't yet (#158).

### Compatibility fixes

- **`Type` and `MemberInfo` through BinaryFormatter (#156).** webForCore's BinaryFormatter writes `Type`, `MethodInfo`,
  `ConstructorInfo`, `FieldInfo`, `PropertyInfo`, `EventInfo`, `Missing`, `Assembly` and `Module` as .NET Framework 4.8
  does (`System.UnitySerializationHolder`, `System.Reflection.MemberInfoSerializationHolder`) and reads them from .NET
  Framework's streams. They were "not marked as serializable": Orchard 1.10's cache of NHibernate's configuration
  failed on every start, as did a `Type` in session state, view state or a binary cache. Tested against streams .NET
  Framework 4.8 wrote, which the port reads and writes byte for byte.
- **Settings classes (#154).** `ApplicationSettingsBase` (Visual Studio's `Settings.settings` classes, and the `Url` of
  every "Add Web Reference" SOAP client) threw `TypeLoadException` ("Could not resolve type
  'System.Configuration.Internal.ConfigurationManagerInternal'"): Umbraco 7.15's upgrade check failed. Settings are read
  from `<applicationSettings>` in web.config again; a user-scoped setting throws `ConfigurationErrorsException` in a web
  application, as on IIS, and works in a console application.

### Upgrading from 0.8.0

- Remove a `<Reference>` to a copy of .NET Framework's `System.Data.Linq.dll`, if the application has one: the
  `webForCore` package brings webForCore's.
- `<add assembly="System.Data.Linq, ...">` entries in web.config can stay. MIGRATING.md no longer says to remove them.
- A directory's default document is now the name the `<defaultDocument>` list gives (`/` is `/default.aspx` with
  IIS's list, as on IIS), not the file's name on disk (`/Default.aspx`), and `Request.RawUrl` is the directory (#127).
  Code that compared either with the file's own name compares ignoring case, as it had to on IIS.
- Change a binding redirect or `<add assembly>` entry that names webForCore's old versions (`WebGrease,
  Version=11.0.0.0`, `System.Web.Extensions, Version=11.0.0.0`, ...) to Microsoft's: a reference to 11.0.0.0 no longer
  loads. The ones Visual Studio and NuGet wrote for .NET Framework are right as they are.

### Migration guide

What the smoke test's migrations found, in [MIGRATING.md](../MIGRATING.md) and
[AGENT-MIGRATION.md](../AGENT-MIGRATION.md) (whose blocker search and symptom table have each), and
[NAMESPACES.md](../NAMESPACES.md):

- **Not on .NET, now in the blocker search:** Windows Identity Foundation (`System.IdentityModel`, IdentityServer3,
  #119), Windows Workflow Foundation (WF3 needs a rewrite; CoreWF covers WF4 only, #132) and WCF Data Services hosting
  (#149).
- **Converting projects:** Web Site Projects with no `.csproj` (`CodeFile=` pages, #131), VB projects
  (`<MyType>Empty</MyType>`, #121), MVC 3 and 4 apps (`webpages:Version`, `[Compare]`'s `CS0104`, #122), types .NET
  added (`KeyValuePair`'s `CS0104`, #136), design-time classes (#144), plug-in libraries built into their own folder
  (#150), and C# 14's span conversions breaking LINQ to Entities at run time (#138).
- **Packages:** WebMatrix.Data and WebMatrix.WebData are Microsoft's 3.2.9 packages (#130),
  `Microsoft.Data.Services.Client` 5.8.4 replaces `System.Data.Services.Client` (#149), an app's own Roslyn must be
  5.9.0 (`NU1107`, #153), and Autofac.Configuration 3, Castle.Core 3 and NHibernate 4 need newer versions (#148).
- **Code:** `AppDomain.DynamicDirectory` is null (use `HttpRuntime.CodegenDir`, #139), `Thread.ResetAbort()` throws
  (remove it, #143), the parameterless crypto factories throw (use the old defaults, #151), System.CodeDom can't
  compile (use webForCore's provider, #133), and ICU gives `en-US`/`en-GB` three decimals for `F` and `N` (#124).
- Web API OData runs since LINQ to SQL is provided (#120, above).

### The SQL providers' database: webforcore-regsql (#123)

Applications on ASP.NET's SQL providers (`SqlMembershipProvider`, `SqlRoleProvider`, `SqlProfileProvider`,
personalization, `SqlWebEventProvider`) and SQL Server session state can create their database. webForCore had none
of the scripts `aspnet_regsql` and `SqlServices` run: `SqlServices.Install` threw `FileNotFoundException` for
`InstallCommon.sql`, and MVC Music Store's Register and LogOn were a 500.

- **System.Web carries .NET Framework 4.8's scripts** (read as data from its folder; referencesource doesn't have
  them), and `System.Web.Management.SqlServices` reads them, so `Install`, `InstallSessionState` and the
  `Generate...Scripts` methods work as on .NET Framework.
- **`webforcore-regsql`**, the .NET tool `webForCore.RegSql`, has aspnet_regsql's switches: `-A`/`-R` features,
  `-ssadd`/`-ssremove`, `-sqlexportonly` (byte for byte aspnet_regsql's script) and SQL cache dependency
  (`-ed`/`-et`/`-lt`...). MIGRATING.md section 5 says how to move an application off `LocalSqlServer`'s SQL Express
  `aspnetdb.mdf`.

### Fixes

- **`Server.MachineName` works on Linux** (#128). It called kernel32's `GetComputerName` and threw
  `DllNotFoundException`, so ELMAH's `/elmah.axd/rss` and `/elmah.axd/json` failed and `/elmah.axd` was empty (Wingtip
  Toys). It is `Environment.MachineName`, the same name on Windows; on Linux the host name, as it is.
- **webForCore's `CSharpCodeProvider` takes .NET Framework's `CompilerParameters`** (#135). `CompilerOptions = null`
  threw `NullReferenceException`, and `GenerateInMemory` without debug information `ArgumentNullException`. Every
  combination of `GenerateInMemory`, `IncludeDebugInformation`, `CompilerOptions`, `OutputAssembly` and
  `TempFiles.KeepFiles` now gives .NET Framework 4.8's results and leaves its files. The 0.8.0 workaround in
  MIGRATING.md is gone.
