## What's new in 0.10.1

### Fixes

- **No change for Subtext's forbidden paths, which answer 301 on 0.10.0** (the smoke test). Request filtering still
  answers 404.8 for a hidden segment (`/App_Data/`, `/bin_dotnet/...`) before any module runs, as on IIS. Subtext's
  Web.config sends every 404 to an error page by `<httpErrors errorMode="Custom">` `ExecuteURL`, and the page's URL
  (`/Subtext.Web/pages/...`, the folder Subtext was developed in) makes Subtext's `BlogRequestModule` redirect the child
  request permanently. Since 0.10.0 the response is the child request's, with its status, as on IIS 10 (#192); 0.9.0
  put the 404 back on it and sent Subtext's 301 as a 404 with a `Location`. IIS.Gate.Tests' `ErrorsAndLimitsTests` pin
  this, and CI's `iis-compare` job checks the same requests against IIS 10. An application that wants a 404 from its
  `ExecuteURL` page sets `Response.StatusCode = 404` there, or points `<httpErrors>` at a URL the application serves.
- **Web.config's `<system.diagnostics>` is applied** (#213, found by #203). Its trace listeners, sources, shared
  listeners and switches were never created: .NET's System.Diagnostics reads configuration only through
  `TraceConfiguration.Register()` in .NET's System.Configuration.ConfigurationManager, which webForCore replaces with
  .NET Framework's System.Configuration, and webForCore's machine.config declared the section as an `IgnoreSection`. So
  a `TextWriterTraceListener` log, Web API's tracing (`EnableSystemDiagnosticsTracing`) to a Web.config listener, and
  libraries' `TraceSource`s wrote nothing. System.dll's classes for the section come back from the reference source,
  and webForCore's System.Configuration has .NET's `System.Diagnostics.TraceConfiguration.Register()`, which System.Web
  calls at start: `<trace autoflush indentsize>` and its `<listeners>`, `<sources>` (`switchValue`, `switchName`,
  `switchType`), `<sharedListeners>`, `<switches>`, `<assert>`, filters, `initializeData` (relative to Web.config's
  folder), attributes, listener types from the application's assemblies or by System.dll's names
  (`TextWriterTraceListener`, `XmlWriterTraceListener`, `DelimitedListTraceListener`, `EventLogTraceListener` on Windows),
  and `Trace.Refresh()` for sources and switches. WebApi.Gate.Tests' `SystemDiagnosticsTests` check each, and CI's
  `iis-compare` job the same requests against IIS 10. What .NET doesn't let configuration do: `Trace.Refresh()` leaves
  Trace with .NET's default listener and settings, not `<trace>`'s (a known difference); an error in `<trace>` stops
  the application at start rather than at its first trace; unsupported attributes aren't rejected
  ([NAMESPACES.md](../NAMESPACES.md#systemconfiguration-srcwebformsforcoreconfiguration)). The webForCore.Configuration
  package now depends on System.Diagnostics.EventLog, as .NET's System.Configuration.ConfigurationManager does.
