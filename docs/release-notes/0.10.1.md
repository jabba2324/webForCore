## What's new in 0.10.1

### The IIS site's ID

- **`WebForCore:Host:SiteId`** (#210), the IIS site's ID, 1 by default (IIS's Default Web Site). Since 0.10.0
  `HttpRuntime.AppDomainAppId` is IIS's `/LM/W3SVC/1/ROOT`, so every application on one machine had the same ID, and
  what ASP.NET keys by it was shared between unrelated applications: SQL Server session state's rows in a shared
  session database, `<machineKey>` keys derived with `IsolateByAppId` (two applications accepted each other's forms
  tickets), and the compilation lock. The application's ID and `APPL_MD_PATH` are now `/LM/W3SVC/<SiteId>/ROOT` (and
  `/ROOT/<path>` under a virtual path), `INSTANCE_ID` is the site ID and `INSTANCE_META_PATH` `/LM/W3SVC/<SiteId>`, as
  on IIS. The host gives it to its workers; an application run on its own reads the same key from its configuration.
  A host with a site ID below 1 doesn't start. **The servers of a farm use the same site ID** (the default is fine);
  **different applications on one machine use different ones** (MIGRATING.md, "Session state"). Without the setting
  nothing changes. SessionCache.Gate.Tests' `SiteIdTests` run two instances with different site IDs (no shared
  sessions or tickets) and two with the same one (shared), and Host.Tests the setting.

### Fixes

- **No change for Subtext's forbidden paths, which answer 301 on 0.10.0** (the smoke test). Request filtering still
  answers 404.8 for a hidden segment (`/App_Data/`, `/bin_dotnet/...`) before any module runs, as on IIS. Subtext's
  Web.config sends every 404 to an error page by `<httpErrors errorMode="Custom">` `ExecuteURL`, and the page's URL
  (`/Subtext.Web/pages/...`, the folder Subtext was developed in) makes Subtext's `BlogRequestModule` redirect the child
  request permanently. Since 0.10.0 the response is the child request's, with its status, as on IIS 10 (#192); 0.9.0
  put the 404 back on it and sent Subtext's 301 as a 404 with a `Location`. IIS.Gate.Tests' `ErrorsAndLimitsTests` pin
  this, and CI's `iis-compare` job checks the same requests against IIS 10. An application that wants a 404 from its
  `ExecuteURL` page sets `Response.StatusCode = 404` there, or points `<httpErrors>` at a URL the application serves.
