## What's new in 0.10.1

### Fixes

- **No change for Subtext's forbidden paths, which answer 301 on 0.10.0** (the smoke test). Request filtering still
  answers 404.8 for a hidden segment (`/App_Data/`, `/bin_dotnet/...`) before any module runs, as on IIS. Subtext's
  Web.config sends every 404 to an error page by `<httpErrors errorMode="Custom">` `ExecuteURL`, and the page's URL
  (`/Subtext.Web/pages/...`, the folder Subtext was developed in) makes Subtext's `BlogRequestModule` redirect the child
  request permanently. Since 0.10.0 the response is the child request's, with its status, as on IIS 10 (#192); 0.9.0
  put the 404 back on it and sent Subtext's 301 as a 404 with a `Location`. IIS.Gate.Tests' `ErrorsAndLimitsTests` pin
  this, and CI's `iis-compare` job checks the same requests against IIS 10. An application that wants a 404 from its
  `ExecuteURL` page sets `Response.StatusCode = 404` there, or points `<httpErrors>` at a URL the application serves.
- **`__VIEWSTATEGENERATOR`, and `<machineKey>` `IsolateApps` and `IsolateByAppId` after an explicit key, are .NET
  Framework's** (#212). On .NET Framework they come from `StringComparer.InvariantCultureIgnoreCase`'s hash of the
  page's directory and class name, the virtual path and the application ID: a non-randomized hash of the string's
  Windows NLS sort key, which .NET doesn't have. webForCore now builds that sort key from a table of the weights .NET
  Framework 4.8 gives on Windows Server 2022 and 2025, and hashes it the same way, so a page renders IIS's
  `__VIEWSTATEGENERATOR` (`linq/Products.aspx`: `D1602CB0`, was `73C738F5`), and forms tickets and `MachineKey.Encode`
  output with `IsolateApps` or `IsolateByAppId` read on both in a mixed farm. Every ASCII and Latin string, and most
  other scripts, are reproduced; a path or name with kana, conjoining Hangul jamo, private use or supplementary
  characters keeps webForCore's own hash ([IIS-COMPATIBILITY.md](../IIS-COMPATIBILITY.md#net-frameworks-string-hash)).
  System.Web.Mobile's `MobilePage` used .NET's randomized hash for its view state MAC key, which changed in every
  worker process; it uses the same hash now. IIS.Gate.Tests' `InvariantHashTests` and `MachineKeyInteropTests`, and CI's
  `invariant-hash-framework-data`, `machinekey-framework-interop` and `iis-compare` jobs check it against .NET Framework
  4.8 and IIS 10.
